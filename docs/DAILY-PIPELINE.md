# 日次処理仕様（暫定）

## 入力と順序

1. 信頼済みのサーバーが、Asia/Tokyoでの「処理対象日」を判定する。
2. 対象日の投稿を取得し、ユーザーごとに**サーバー付与のrevision最大1件**を抽出する。過去の投稿編集は不可。
3. イベント強度を**サーバー側で**決定する。デフォルトはN=1。クライアント指定のNは無視する。
4. 前日マップ上の同じ座標の勢力と、最終投稿から成る候補を衝突ルールで解決する。
5. 投稿を反映した前日マップを入力に、**1日1世代**の受動的侵食を実行する。
6. スナップショットを日付付きで保存する。処理対象は必ず前日の翌日とする。

この順序は暫定判断。投稿前に侵食する案とは結果が異なるため、正式仕様決定時にテストを更新する。

## DBと定期実行の契約（未実装）

- 投稿APIでは認証済みの内部ユーザーIDのみ使用し、revisionはDBトランザクション内で付与する。
- (user_id, day)の現在値は常に最大revisionで一意に決まる。
- 同時編集時、DBロック / CAS / SERIALIZABLEのいずれかで直列化する。
- 日次生成では対象日につき単一実行ロックを取得し、完了済みsnapshotがあれば再実行は内容照合して冪等に終了。
- マップと投稿の一貫性を保つため、対象日締切後に投稿集合を固定して計算。
- DBに識別可能な個人情報や秘密鍵、セッションIDをスナップショットとして保存しない。
- パスキーWebAuthnのcredential ID・公開鍵・signature counterは認証専用の非公開DB領域に分離。
- 認証、予約投稿、サイトの公開はまだ実装していない。

## 再現性とセキュリティ

計算は純関数であり、同じ前日state、同じrevision一覧、同じイベント強度と範囲から同一stateになる。保存時にはスナップショットのJSON正規化とハッシュ管理を推奨。

対応できていないもの: 投稿API認証、レート制限、CSRF、WebAuthn RP ID/originの検証、複数セッション、失効、監査ログ。これらなしに一般ユーザーの投稿を受け付けてはいけない。
