# 日次投稿・公開stateのパイプライン（開発版）

## 1. 投稿反映と計算順序（暫定ゲーム仕様）

1. サーバー時刻を \`Asia/Tokyo\` で区切り、ユーザーの操作日を決定する。
2. 認証済み内部ユーザーIDについて \`(user_id, day)\` に1レコードを確保し、同日の再投稿は \`revision\` を原子的に加算して文字・座標を上書きする。
3. 対象日の投稿を閉じた後、前日の公開stateとその日の最終投稿のみを取り出す。
4. 投稿勢力値 \`N\` はサーバー側が決める（通常N=1、イベント時は別の強さ）。クライアントが任意のNを指定するAPIはない。
5. 既存勢力と同座標への投稿を衝突計算し、**その結果を入力**に、上下左右から1日1世代の受動的侵食を同期計算する。
6. \`state-YYYY-MM-DD.json\` 相当の新stateを永続化し、閲覧専用API・静的JSONへ公開する。

投稿反映後に侵食する順序や現住者防御・同文字合算等は暫定仕様。 \`docs/ALGORITHM.md\` とIssue #1–#3を参照。

## 2. SQLite開発版（実装済み）

- \`server/store.mjs\` がNode.js実験的 \`node:sqlite\` を使い、DBトランザクション \`BEGIN IMMEDIATE\` により投稿更新・イベント設定・日次公開を直列化する。
- \`posts\` は日付×ユーザーあたり**現在の最終版1レコードのみ**を持ち、過去版の履歴は保存しない。 \`revision\` は同日変更回数の追跡に利用する。
- \`snapshots\` は日付を主キーに持ち、JSON本体とそのSHA-256を保存する。
- 状態公開に失敗した場合はトランザクションをロールバックし、前日stateと投稿レコードを保持する。
- 確定済みstateの再公開要求は同じstateを返す（本番用の再計算によるハッシュ一致確認は未実装）。
- \`scripts/run-server.mjs\` は開発時に1時間おきに対象日を確認する。 \`scripts/daily-job.mjs\` は一回だけ処理するCLI。
- \`scripts/export-states.mjs\` は公開stateだけを出力し、各ファイルのバイト列のSHA-256を \`data/index.json\` に記録する。

## 3. セキュリティ責務

- \`server/http.mjs\`: WebAuthnの署名、challenge一回消費、Origin/RP ID、userHandle、cookieによるセッション確認を実施する。
- 公開地図データは文字・座標・N・日付のみ。ユーザーIDや認証情報は返さない。
- POSTはOriginヘッダー、Content-Type、JSONサイズ制限で保護。IPごとのメモリ内レート制限を適用。
- 端末での秘密鍵・生体認証はWebAuthnの範囲で扱い、バックエンドには秘密鍵を保存しない。

## 4. 本番へ移行するときの未実装・検証事項

- GPT SitesがサーバーAPI、DB、WebAuthn、スケジューラをサポートするかの実際の確認。
- 365日以上の計算持続性（現行同文字合算は52日でオーバーフロー）。
- 複数サーバー・同時アクセス下のトランザクション・キュー・ロック・エラーハンドリング。
- サーバー側の投稿受付締切とクライアント時刻との食い違い・復旧・耐障害性。
- 正式ドメインRP ID、Secure Cookie、DoS・CSRF、アカウント復旧、データ削除・バックアップ。
- サイト公開のテスト、利用規約・運営主体・保持期間・広告の適法性。
