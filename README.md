# EROSION MAP — 1日1文字 侵食マップ

[ソースコード](https://github.com/Unjuno/Erosion-map) · [自動テスト](https://github.com/Unjuno/Erosion-map/actions) · [侵食ルール](docs/ALGORITHM.md)

1日に1文字だけ座標を指定して投稿し、上下左右からの影響を**受け取る側のマス**が計算して日ごとに変化する公開マップ。メールアドレス・パスワードの入力に代わりパスキー（WebAuthn）認証を利用する設計です。

| Sites API | sites/worker.mjs、Fetch API / WebAuthn / D1 / 静的Assets |

## ローカル開発

Node.js 22以上、npm、TypeScript 5.8.3、@simplewebauthn/server 14.0.3、esbuild 0.25.12を想定しています。

```bash
npm install
npm test              # エンジン・DB・API・Worker・UI の自動テスト
npm run dev           # 静的デモ: http://127.0.0.1:4173
npm run dev:full      # ローカルSQLite + パスキー: http://localhost:4173/submit
npm run build:sites   # site/ に静的サイトと _worker.js を生成
npm run preflight     # 本番公開の前提条件を判定（未確認なら失敗）
```

`site/` は生成物であり、Gitにコミットしません。公開リポジトリには生きたDB、個人情報、秘密鍵、セッションCookie、認証チャレンジを置かないでください。

## GPT Sites向けの実装

- `sites/worker.mjs` — Web標準の `fetch` / `scheduled` イベント
- `sites/d1-store.mjs` — 非同期D1 APIへのアクセス
- `migrations/0001_d1_schema.sql` — D1のテーブルと一意制約
- `migrations/0002_day_closure.sql` — 投稿締切時の確定・投稿競合を防ぐDBトリガー
- `migrations/0003_closed_post_capture.sql` — 締切時に匿名投稿をトランザクション内で凍結する
- `migrations/0004_archival_and_chunked_states.sql` — 締切前の退会でも過去の匿名投稿を保持し、2MBを超える公開stateをチャンク保存する。既存の公開済み投稿の個人識別情報を消去する
- `migrations/0005_durable_rate_limits.sql` — 認証開始・投稿更新をD1で原子的に回数制限する（短期間のハッシュ化カウンター）
- `.openai/hosting.json` — DBバインディング名 `DB` の設定（サイトIDや秘密情報は含めない）
- `scripts/build-sites-worker.mjs` — `site/_worker.js` のバンドル
- `public/` — HTML、CSS、Canvas、パスキー投稿画面

本番環境の設定には次が必要です。

| 設定 | 意味 |
|---|---|
| `DB` | D1データベースバインディング、SQL migration適用済み |
| `ASSETS` | `site/` の静的アセットを配信するバインディング |
| `PUBLIC_ORIGIN` | 最終HTTPSサイトの正確なOrigin |
| `RP_ID` | パスキーの依拠当事者ドメイン |
| `SAME_GLYPH_MODE` | 既定 `max` （v1候補）／従来 `sum` |
| `N1_OUTBOUND` | 既定 `1` （v1候補）／従来 `0`、1はmax限定 |
| `RATE_LIMIT_SECRET` | 任意だが本番では推奨。32文字以上の非公開ランダム値。信頼できるホストの`CF-Connecting-IP`から生IPを記録せず、ハッシュ化された短期レート制限キーを作る。未設定時はサイト全体の制限にフォールバック |
| `MAX_CATCHUP_DAYS` | 予約イベント1回で処理する最大日数。既定2、1〜32。利用可能なD1クエリ上限を検証した場合だけ増やす |

**SQL migrationは必ず0001→0002→0003→0004→0005の順にSitesのD1へ適用してください。** 0004は0003の締切トリガーを更新し、失われる前の過去投稿を匿名退避する表と、公開stateの分割保存表を作成します。移行前に既に削除された投稿は復旧できません。0004は公開済みの識別子付き投稿を消去するため、必ず本番DBをバックアップしてから適用してください。未移行の古いアプリコードと新しいDBを同時稼働させないでください。認証情報やDBの中身はGitHubに置かないでください。

Sites D1のBLOBは読み出し時に`number[]`となるため、その形式を受け付ける公開鍵デコードを実装しています。大きな公開stateは、連続する同一文字・同一Nのマスをカラム単位で可逆圧縮する`@rle-snapshot:v1:`形式で保持します。圧縮効果が小さい場合は従来のJSONまたはチャンク形式にフォールバックし、どの場合も**展開後の公開JSON全体**のSHA-256を検証します。既存のJSON形式とチャンク形式の読み出しは維持しています。大規模マップのCPU/メモリ負荷・日次ジョブの実行時間は別途実機で検証する必要があります。 認証開始のサイト全体上限は5分あたり240回、`RATE_LIMIT_SECRET`と信頼できる接続元IPがある場合は5分あたり1接続元20回、接続元を識別できない場合は5分あたり120回です。認証済みの投稿更新は1ユーザーあたり1分30回までとします。この制限はD1の負荷を軽減するための補助策であり、外部WAFや実際のSitesホスティングの制限を代替しません。

サイトの公開操作・D1作成・実運用のスケジュール設定は、このソース管理とは別にGPT Sites上で行います。`scheduled` イベントが利用できない場合は閲覧時に1日分を補完する実装がありますが、厳密な時刻での無訪問更新を保証しません。

## 侵食ルールの未確定点

元の要件にある「通常投稿N=1」と「隣接への影響はN−1」は同時に採用すると、通常投稿が広がらないという矛盾があります。

- [#1](https://github.com/Unjuno/Erosion-map/issues/1): N=1の伝播をどう実現するか（Sites v1候補: `max+最低影響1`）
- [#2](https://github.com/Unjuno/Erosion-map/issues/2): 多勢力相殺・同文字の合算などの正式ルール
- [#3](https://github.com/Unjuno/Erosion-map/issues/3): 同文字加算に伴う長期数値オーバーフロー

動作するサイトを成立させるため、Sites Workerの**v1候補デフォルト**を `max + N1_OUTBOUND=1` に設定しました。通常のN=1投稿を翌日に周囲へ広げ、同文字の影響値の発散を避けます。元仕様の `sum,N−1` も環境変数で指定できますが、数値発散と不拡大の問題があり推奨しません。これは**元仕様からの明示的な変更提案**であり、ユーザーによる最終確認はまだ完了していません。 [ルール比較](docs/RULE-COMPARISON.md)を参照してください。

## 継続運用の検証条件

`src/engine.ts`はSites候補のmax方式で小〜中規模の格子を型付き配列によって計算し、従来sum方式と巨大な疎グリッドは従来の参照実装を維持しています。同期・受動的な衝突規則は変更しません。ランダム化差分テスト（独立した参照計算）によって互換性を検証しています。

`npm run benchmark:365` は500×500・中央N=1・365世代のNode単体試験です。CIでは96MiBのV8旧世代ヒープ上限も確認します。これとは別に`scripts/benchmark-d1-365.mjs`で365件の公開日（初期状態を含め366スナップショット）をNodeのSQLiteでD1互換APIとして一括検証します。これらは**ChatGPT Sitesの実際の128MB isolate・D1制限を検証したものではありません**。実機・D1負荷・並列リクエスト・復元試験は本番公開前に必須です。

大量の閉鎖日を1回のscheduled Worker実行で処理すると、D1のクエリ上限を超える可能性があります。既定の上限を2日に絞りましたが、巨大スナップショットでは更なる分割実行が必要です。履歴の遅延を自動で解消する運用スケジュールと復旧手順は実環境で検証してください。
